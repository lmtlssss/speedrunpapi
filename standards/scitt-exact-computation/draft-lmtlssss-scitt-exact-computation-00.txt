               Exact Computation Claim Profile for SCITT
               draft-lmtlssss-scitt-exact-computation-00

Abstract

   This document proposes an application profile for statements about
   exact computational claims.  Each statement binds an artifact digest,
   a claim, its input domain, a verifier version, and evidence.  The
   statement uses SCITT COSE signing and can carry a transparency
   receipt.  A relying party checks the computational evidence
   separately from the issuer signature and transparency receipt.

1.  Introduction

   A computational artifact can have different claims about its
   behavior.  These claims can refer to output uniqueness, witness
   uniqueness, deterministic execution, or a checked counterexample.  A
   signed claim needs an exact scope and an independent verification
   procedure.  The SCITT architecture in [RFC9943] supplies a signed
   statement and transparency receipt framework.

   This document proposes a payload profile.  It does not define a new
   mathematics or claim that a signature proves a computation correct.

2.  Signed Statement

   An issuer uses the COSE_Sign1 Signed Statement format in [RFC9943].
   The protected header identifies the issuer and subject through COSE
   header parameter 15, the CWT Claims header defined by [RFC9597].  It
   also identifies the algorithm, key and payload content type.  This
   initial proposal uses application/cbor for the payload.  The payload
   contains the profile identifier taa.exact-computation-claim.v1.

   A transparency service can register the statement and return a
   receipt under [RFC9942].  The receipt attests to registration under
   that service's policy.  It does not attest to mathematical
   correctness.

3.  Claim Payload

   The initial map uses integer keys.  The artifact digest and evidence
   digest are SHA-256 values over exact byte streams.  The verifier
   digest identifies the precise checker implementation.  The claim
   includes a predicate identifier, domain, observation contract,
   verdict and assumptions.

   exact-claim = {
     1: "taa.exact-computation-claim.v1",
     2: artifact,
     3: claim,
     4: verifier,
     5: evidence,
     6: tstr,                  ; issue time, UTC
     ? 7: tstr                 ; replaces statement
   }
   artifact = {
     1: "sha-256", 2: bstr .size 32,
     3: tstr, ? 4: tstr
   }
   claim = {
     1: tstr, 2: tstr,
     3: "certified" / "broken" / "unknown",
     4: tstr, 5: [* tstr]
   }
   verifier = {
     1: tstr, 2: tstr,
     3: "sha-256", 4: bstr .size 32
   }
   evidence = {
     1: "sha-256", 2: bstr .size 32,
     ? 3: tstr, ? 4: tstr
   }

4.  Claim Semantics

   The certified verdict states that the named checker accepted the
   declared predicate for the declared domain.  The broken verdict
   identifies evidence of a counterexample.  The unknown verdict states
   that the checker established neither.  Output uniqueness requires
   exact output-set preservation.  Witness uniqueness additionally
   requires witness-fiber preservation or exact witness counting.

5.  Relying Party Procedure

   1.  Parse the COSE_Sign1 envelope and check the protected headers.

   2.  Select the issuer trust anchor and verify the COSE signature.

   3.  Parse the CBOR payload and require the supported profile version.

   4.  Calculate and compare the digest of the exact artifact bytes.

   5.  Obtain the specified verifier and compare its digest.

   6.  Obtain evidence, compare its digest, and execute the independent
       checker.

   7.  Compare the checker outcome with the declared claim and local
       trust policy.

   8.  Validate SCITT receipts when the local policy requires
       transparency.

6.  Security Considerations

   Issuer signatures authenticate statements and do not prove their
   claims.  A checker can have an implementation error or omit an
   assumption.  A relying party must bind the exact source bytes, claim,
   verifier version and evidence.  A receipt establishes transparency
   service registration and does not establish computational
   correctness.  Key compromise, issuer identity, superseded claims,
   private inputs and evidence availability require explicit local
   policy.
